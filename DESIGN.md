# Desktop design contract

Mode: Operate. Preserve the dashboard's Survey Sheet design.

The Reoclo web dashboard's design system and its Button, Input, Table, StatusBadge, InfoField and PageHeader components are the visual authority. The desktop translates their semantic tokens into Rune, rather than treating the native app as a website.

- Light: paper background, deeper paper sidebar, ink foreground. Dark: night chart background with warm light foreground.
- One-pixel rules separate surfaces. No shadows. Corners use 2, 3 and 4 point radii.
- Figtree for controls and prose, Mona Sans for page titles, JetBrains Mono for machine values. Embedded font assets retain their licenses.
- Spacing: 4, 8, 12, 16, 24, 32 points. Body 14 points, labels 12, section headings 18, page titles 28.
- Status: square success for Active, triangular warning, circular information, diamond failure, filled neutral dot for Ready, and an outlined neutral ring for inactive states. Ready means listening without an open session. Every mark has a text label.
- Four button ranks: primary (flat foreground/background contrast), secondary (a one-point rule), danger (a one-point danger rule, for an action that opens a confirmation), and destructive (filled danger, only for the button that confirms). Offer the action the current state allows rather than disabling the others. In a dialog the primary action is rightmost, with Cancel to its left. Orange belongs to selection and focus. Destructive actions require explicit confirmation.
- Theme follows the system unless the user chooses light or dark. Motion uses Rune's virtual clock and reduced-motion support.

Layout: Main window uses a split view with sidebar navigation and a toolbar. Its content scrolls within the window. The sidebar has no section heading. Tunnels places the selected tunnel's details and traffic above its table; without a selection it shows combined traffic. Pending approvals remain above the table. The table takes every row when they fit below the details, graph and approvals. Otherwise it fills the rest of the page with as many whole rows as fit, never fewer than four, and scrolls inside itself. The column header stays above the rows, so no row starts under it. While the rows overflow, a thumb on the right edge shows at all times how far they run, and the bottom edge fades while rows are hidden below it. Saved rows keep their On switches. Terminal forwards are rows in the same table, marked Terminal, with a confirmed Stop in the action column. Each TCP forward offers Add HTTPS for its own target. Terminal rows remain visible without saved tunnels. No horizontal overflow at the minimum supported desktop size.

Layout: Add tunnel is a modal form with a single scrolling body and visible Cancel and Save actions. Organization selects the server list; server selects the scanned ports. The manual target remains available.

The form is two columns and fits without scrolling in its usual state, with Kind first because it decides the rest. The HTTPS hostname preview stays outside the scrolling form body. A fading edge and native scrollbar reveal overflow when a warning or error adds height. Kind labels are uppercase; the wire values remain lowercase. Selects and inputs share one height and rule. An HTTPS hostname is an optional subdomain on a trusted domain chosen from a list; without a trusted CA the form offers to trust it and stays open so it can be saved next. Certificates trusts another domain, and Hosts registers and removes hostnames of your own. The port 443 relay has a switch that reinstalls the helper after a confirmation, and says when another program holds port 443. Every helper reinstall keeps the relay and the trusted domains outside .localhost. A trusted domain you added has Remove, which reissues the CA without it after a confirmation; a stale CA offers Trust new CA. Form dropdowns can be searched, and every floating menu has a one-point rule so it reads against the surface it opens over.

Layout: Menu-bar panel. Direction: a ledger an engineer reads in a few seconds. The panel is 340 points wide and as tall as its content, up to 620 points, with a fixed header and footer around one list that scrolls once the panel reaches that height. The window fits the panel, so a quiet list leaves no empty space under its rows. Every part of the panel shares 16 point side padding. The header and footer keep 12 points above and below their content, the space the list leaves under its top rule. The header carries the mark and wordmark with "N of M active" and a diamond with the failure count. Below it, an activity line gives the In and Out rates beside a 16 point line of the last 15 minutes, in the main graph's information and success colors. Anything that needs a decision comes before the tunnels: pending approvals with Deny and Approve on their action line, and a verified update with Restart, separated from the tunnels by a rule. An approval's request sentence and its agent with the expiry sit under the action label's text edge, 4 points apart, and a machine value stays on the line of the word before it, so "port 8080" never splits. The list then follows the main table's order, except that enabled tunnels that failed move to the top with their reason on a second line in the danger color. Every tunnel takes one 28 point line: state mark, name in a 112 point column, endpoint, then a 48 point slot for the switch, or Stop for a terminal forward. Columns sit 8 points apart, and the endpoint's 4 point inset puts its text 12 points from its neighbors. Terminal forwards are ordinary rows showing their server with a Terminal tag, with no separate section and no This Mac heading. The server truncates and the tag never does, so both stay inside the name column. In these rows the mark carries the state alone, with the state as its accessible name and tooltip. Pressing the endpoint copies it. Hostnames truncate at the end, keeping the part that tells them apart, with the full endpoint in the tooltip; address and port endpoints fit whole. Active or Ready web tunnels add an arrow that opens them, and rows without one give the endpoint that width. Names open the window with the row selected. Twelve rows and an approval fit at 340 x 620 without scrolling. The footer keeps Open Reoclo and Quit Reoclo. The menu bar item follows a setting: icon, icon and name, icon and active count, or icon and a meter of one bar per tunnel. Pending approvals and a failure flag show in every style. Meter bars are solid for active tunnels, short stubs for enabled failures, and outlined otherwise.

Layout: First run replaces the main window on first launch and from Settings as Run setup again, until Done. A step rail on the left lists Log in, Set up this Mac, Tools for your agents and Ready for your agent, each with a status mark. One screen shows at a time, chosen from what the daemon, the system and the command worker report, never from a stored step. Each screen has a heading, a body and one primary action at the bottom right, keyed `first-run-next`. A step that raises a macOS prompt explains it first, saying whose password it wants and that Reoclo never sees it, and only Continue raises it. A failure shows its message above the step and keeps the same screen, so the action can be tried again. Log in starts the service, then the device flow, and opens the browser once. If the service does not answer within 20 seconds, the screen fails with Try again. Tools links the app's own command and adds one marked block to the shell settings, or leaves another reoclo alone and says so. Ready shows the prompt to copy and, when Claude Code or Codex is found, Connect your agents with each result beside its name. Done is the primary action and sets the onboarded preference; closing the window any other way brings first run back next launch.

Layout: A `reoclo://open` link always opens a confirmation first, saying what will be reached, on which server, in which organization, and as HTTPS or a local port. Cancel drops it. Confirm signs in if needed, checks the organization and server, reuses a saved tunnel for the same server, kind and target or adds one, then opens the HTTPS address or copies the TCP endpoint. A tunnel that is Ready or Active counts as reached. Invalid links show an alert and change nothing. While first run is open the confirmation waits: the Log in screen shows what the link reaches as Log in and open, Cancel drops it, and Done opens it once setup is finished.

Priorities: tunnel state and endpoint first, server and transport second, traffic and diagnostics third. No decorative metrics or promotional copy. Required data remains present through empty, loading, disconnected, signed-out and error states.

While the sidebar is open it carries the main window's only wordmark, with the hexagon mark. When the sidebar is collapsed, the mark and wordmark sit in the top bar beside the sidebar toggle. The toolbar reserves its trailing slot for real status: a disconnected daemon, work in progress, or the last confirmation. Failures appear under the page title, where they cannot be scrolled past. Mono is for machine values, never prose. Status words always carry their mark. The selected table row and sidebar use the same selection token. Switches describe saved intent: the column is "On" and the accessible label is "Run <name>". They use a light thumb in both appearances, on a track at least 3:1 against it.

Native desktop acceptance: window at 1100 x 760 and minimum 760 x 620; panel 340 points wide and fitted to its content up to 620 points tall. Panel captures crop to the panel, so each one records the height it opens at. A 390 point compact capture checks narrow content behavior, but this is not an iPhone app and mobile safe areas do not apply. Light and dark are captured for every required view and state. Rune PNGs and element trees are the visual evidence; browser-only detectors do not apply to the native renderer.

Updates: Settings places Updates before Desktop app, using the existing setting rows and semantic status marks. Current version and last-check time remain visible beside Check now or Restart to update. Automatic checks default on and persist in the app preferences. A download is labelled as downloading until its SHA-256 and Ed25519 signature pass and the extracted bundle version matches. Ready updates include release notes. Update failures stay in this section without an alert dialog. Outside a writable app bundle, the section explains why updates are off.

Updates: The panel lists a verified update at the top of its list, with the version and Restart. It stays quiet during checks and failures. Restart always requires a click. The app stages the replacement on its own volume and waits for the current process to exit before swapping bundles and opening the new copy. A failed relaunch restores the previous bundle. Tunnels keep running in the daemon.

Updates: Settings remains accessible when the daemon is disconnected. Its loading layout keeps the live Updates section because desktop update state does not depend on daemon data. Capture update-available and update-ready in both themes for Settings and the panel, including compact widths. Interaction tests exercise the automatic-check switch and both restart buttons.

Layout: Tunnels pins its title and two-part summary above its scroll view. The summary is "N of M active", with a diamond and "N failed" when needed. Identical failure details shared by at least two tunnels produce one pinned alert and a group retry. HTTPS port conflicts offer Settings with the port field focused. The table columns are State, Name, Server, Endpoint and On. State is 148 points; Name and Server fit their values between 96 and 220 points, sharing the available width at the minimum window; Endpoint takes the remainder with a 160 point minimum. Sorting happens only when requested, never on state updates. Server names use middle truncation with a full-value tooltip.

Layout: Non-listening tunnel details place the reason and recovery actions before facts. Open is offered only for Active and Ready; Copy endpoint remains available. Facts use up to four 200 point columns, left aligned, with two columns in compact windows. View logs opens Logs filtered to the selected tunnel. Scheduled recovery shows its attempt and next UTC time with Retry now. The row reads Reconnecting while the detail preserves the underlying failure.

Layout: Main pages cap content at 1200 points. Below 900 points the sidebar collapses and page padding becomes 16 points. The Tunnels loading skeleton includes the summary and Add tunnel control, followed by selected facts when present, the graph and a table that fills the rest of the page. The panel's loading list uses five rows on the panel's row grid, so the fitted panel opens near a typical list's height. Logs and Certificates have matching filter and validation skeletons. The first-run loading skeleton keeps the step rail and one screen's measure with its footer action, so the first screen arrives without shifting.

Traffic: Rune draws two steady lines using semantic information and success colors, with text labels for incoming and outgoing rates. The plot is 96 points high with 2 point strokes. It stores at most 900 one-second samples per tunnel; gaps are zero-filled and counter resets cannot make spikes. Five-second maxima retain bursts in the rendered path. The same graph serves aggregate and selected views, including terminal sessions reported by CLI 0.116.0. The empty graph stays still. No decorative animation is added, and reduced motion applies to native navigation.

Logs: A sidebar page owns the virtualized log viewport. JetBrains Mono rows are 24 points high with UTC timestamps. The tunnel filter is a searchable dropdown that lists All tunnels first, then every saved tunnel and terminal session, a terminal session by its server. It matches a complete name. The dropdown and its open list share one width, 320 points or the page when narrower, the widest a menu opens; the text search takes the rest of the row. View logs opens it with that tunnel chosen; text filtering ignores case. Follow keeps the viewport at the end, while Pause freezes a copy of the visible data set. Copy uses the entire filtered data set. Show log in Finder uses the existing native system action. The latest 10,000 lines are retained, combining daemon log events with the file tail without paired duplicates. Log controls remain usable when the daemon is offline.

Certificates: Trust validates a normalized DNS name as the field changes and again before submitting. Permitted suffixes are `.test`, `.localhost`, `.internal`, `.home.arpa`, `.example` and `.invalid`. Their roots and subdomains are allowed. Public domains and `.local` are excluded. The CLI trust boundary enforces the same policy; legacy unsupported suffixes remain removable. The policy follows RFC 2606 and RFC 6761, RFC 8375 for `home.arpa`, and ICANN resolution 2024.07.29.06 for `internal`.

Layout: Offline, signed-out and error views retain cached tunnels as Unknown with switches hidden. Offline names the attempted socket and offers Copy details. Error names tunneld.log and offers Show log in Finder. First launch without cached rows uses the empty data-state layout. Signed out appears in the toolbar. Approvals show a sentence-case action label and expiry, with Deny before Approve; only the pending control is disabled. The daemon drops a request from its pending list when it expires and refuses to decide it after that, so an expired request leaves the app and the menu bar count rather than offering actions that would fail. Action labels support the daemon's open string vocabulary, including unfamiliar values. Actions reaching beyond this Mac retain the warning tone. Page and dialog titles expose heading roles. Blocking data states expose alert roles.
